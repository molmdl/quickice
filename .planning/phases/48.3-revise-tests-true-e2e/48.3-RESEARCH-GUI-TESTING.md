## Summary

**The headline finding: a true headless GUI e2e that drives the REAL `MainWindow` tab-by-tab is FEASIBLE and FAST — and it finds bugs the existing exporter-level e2e tests structurally cannot.** No existing test constructs `MainWindow` (verified by grep; `test_scancode_bugs_gui_ion.py` imports it only for `inspect.getsource` + the worker class). Today's "GUI e2e" tests instantiate **exporters directly** (`InterfaceGROMACSExporter(parent_widget=None)` etc.) with QFileDialog patched — they never touch panels, handlers, cross-tab state wiring (`_current_*_result`), or the panel→worker→completion-handler flow.

I proved the full chain works headless with a probe that drove, through **real MainWindow handlers only**: hydrate generation (real `HydrateWorker` QThread, 0.10s) → interface via the real viewmodel threaded worker (0.10s) → solute insertion (synchronous handler, 0.12s) → custom molecule insertion (threaded worker, 0.10s) → ion insertion (real `IonInsertionWorker` QThread, 0.10s) → all 4 GROMACS export menu handlers with QFileDialog patched → `gmx grompp` rc=0 on each. Total ≈ 2–5s per full chain including MainWindow construction (~0.4s) and one-time `main_window` import (~5.3s).

**The probe also found a live example of the exact bug class this phase targets:** uploading the *unrenamed* `etoh.gro`/`etoh.itp` pair as a custom molecule through the real panel flow (the way a real user would) produces a `.top [molecules]` entry `etoh 10` while the `.gro` carries residue `MOL` — the repo's own `assert_gro_top_consistent` flags this as FATAL, though `gmx grompp` itself returns rc=0. Every existing test avoids this scenario because its fixtures **pre-rename** the custom molecule to name-consistent `cmet.gro`/`cmet.itp` (44.1-13 precedent) or use synthetic name-consistent files. The same fixture hygiene is why 44.1-UAT's manual test found the "moleculetype etoh is redefined" duplicate-#include failure that 52 passing phase-45/44.1 tests missed.

**Primary recommendation:** Build the GUI e2e as a **MainWindow-driven chain test** (one module-scoped fixture constructing `MainWindow` once, driving handlers in order, exporting all 4 paths + grompp), using the empirically verified env combo `QT_QPA_PLATFORM=offscreen` (+ `DISPLAY=localhost:11.0` set so `is_vtk_available()` returns False and VTK rendering is skipped — this is *protective*, not incidental), the state-polling wait pattern for handler-created workers, a **complete** modal-dialog patch list (main_window + export + panel namespaces — missing `QMessageBox.information` hangs the test), and **mandatory thread cleanup in fixture teardown** (a failing test with live threads SIGABRTs and can poison the whole pytest session).

## 2. Working Headless Patterns Catalog (all verified in-repo; probes where noted)

### Pattern A — QApplication singleton (repo standard)
```python
# Source: tests/test_hydrate_panel.py:51-57 (canonical); tests/conftest.py provides NO qapp fixture
@pytest.fixture
def panel(self, monkeypatch):
    monkeypatch.setenv("QT_QPA_PLATFORM", "offscreen")   # MUST be set BEFORE QApplication creation
    if not QApplication.instance():
        QApplication(sys.argv)
    return HydratePanel()
```
Rules learned the hard way across the repo: set `QT_QPA_PLATFORM=offscreen` **before** any QApplication/QWidget construction; reuse `QApplication.instance()` if present (pytest may run multiple GUI files in one process).

### Pattern B — QFileDialog inline patch for exporters (repo standard for export e2e)
```python
# Source: tests/test_e2e_custom_guest_cross_tab_gui.py:328-331
with patch("quickice.gui.export.QFileDialog.getSaveFileName",
           return_value=(str(gro_path), "GRO Files (*.gro)")), \
     patch("quickice.gui.export.QMessageBox"):
    exporter = InterfaceGROMACSExporter(parent_widget=None)
    ok = exporter.export_interface_gromacs(structure, hydrate_config=config)
```
Under offscreen, an *unpatched* `QFileDialog.getSaveFileName` returns `("", "")` → exporter silently returns False. Exactly one `getSaveFileName` call per export (the `.gro`); `.top`/`.itp` paths derive from `path.stem`. Patch target is the **using module's** namespace (`quickice.gui.export.QFileDialog`), not `PySide6.QtWidgets`.

### Pattern C — QObject workers: call `run()` synchronously (repo standard)
```python
# Source: tests/test_e2e_triclinic_blocking_e2e.py:155-199
worker = InterfaceGenerationWorker(candidate, config)   # QObject, NOT QThread
errors = []
worker.error.connect(lambda msg: errors.append(msg))   # connect BEFORE run()
worker.run()                                            # synchronous; emits signals directly
```
`GenerationWorker` and `InterfaceGenerationWorker` are `QObject`s designed for `moveToThread`; tests skip the thread entirely. **No event loop, no `QTest.qWait`, no flake.**

### Pattern D — QThread workers: `start()` + `wait()` (scancode precedent; probe-verified)
```python
# Source: tests/scancode/test_scancode_bugs_gui_ion.py:91-118
worker = IonInsertionWorker(interface=MagicMock(), concentration_molar=0.5, liquid_volume_nm3=None)
worker.start()
finished = worker.wait(10000)      # block; no event loop needed for thread-side asserts
assert finished
```
For `HydrateWorker`/`IonInsertionWorker` (direct QThread subclasses per AGENTS.md — do NOT "fix" to QObject+moveToThread). Button-lifecycle tests instead mock the worker class and assert `start()` was called (`patch("quickice.gui.main_window.IonInsertionWorker", ...)`).

### Pattern E — Skirt construction: `Panel.__new__(Panel)`
`test_scancode_bugs_ion_charge_warning.py:161` builds `IonPanel` without QApplication to test pure methods (`get_total_charge`). Useful for logic-only tests; no widget tree exists (no `isVisible()`).

### Pattern F — Modal suppression (partial catalog — see Pitfall 2 for the full one)
Existing tests patch only what they trigger: `QMessageBox.warning` (hydrate panel atomtypes warning), `QMessageBox.question` returning `Yes`/`No` (custom panel mismatch dialog), whole `quickice.gui.export.QMessageBox` class (exporter paths). **No existing test needed `main_window.QMessageBox.information` — because no test ever ran a successful export through a MainWindow handler.** (Probes needed it; see §3.)

### Pattern G — VTK availability control
`quickice.gui.vtk_utils.is_vtk_available()` + `reset_vtk_available_cache()` (VTK-DUP fix): returns False iff `DISPLAY` contains `localhost` and `QUICKICE_FORCE_VTK != "true"`; returns **True when DISPLAY is empty or unset** (and for local `:0`). All 6 viewers guard widget creation behind it. Tests that must avoid VTK rendering entirely can either rely on `importorskip("vtk")` (renderer unit tests) or — for MainWindow-level tests — set `DISPLAY=localhost:11.0` so every viewer takes its no-VTK branch (probe-verified; see §3).

### Pattern H — Module-scoped GenIce2 amortization (AGENTS.md mandated)
`test_e2e_custom_guest_cross_tab_gui.py:77-221` builds hydrate ONCE, derives a **fresh `assemble_slab` interface per inserter** (ion inserter mutates `iface.molecule_index` at `ion_inserter.py:259`), seed=42 deterministic. Measured: full 4-exporter grompp file = **1.64s**; 4-lattice cross-tab + builtin regression = **7.51s / 8 tests**.

### Pattern I — Source-grep assertions for MainWindow internals
`test_hydrate_panel.py:363-408` + `test_scancode_bugs_gui_ion.py`: `inspect.getsource(MainWindow._on_export_interface_gromacs)` and assert the call string appears. Cheap regression guard — but it is **assertion-of-text, not execution**; this phase should keep these as cheap guards and ADD execution-level tests (§6).

## 3. Blockers for a True Headless GUI e2e — Evidence + Verified Workarounds

### Blocker 1: Qt XCB C-level hang (the "2-hour hang trap") — env-dependent
**Evidence:** 48.1-14-SUMMARY ("re-running would risk the 2-hour hang trap that hung the previous agent"), 48.2-01/02/03-SUMMARY ("full ~1854-test suite deadlocks at the C level in this headless environment (GUI/Qt/VTK event loops; `DISPLAY=localhost:11.0` forwarded X11, `QT_QPA_PLATFORM` unset); pytest-timeout SIGALRM cannot interrupt C-level hangs"), 48.1-UAT ("excluding 22 GUI tests that hang in headless environment").
**Root cause:** with `QT_QPA_PLATFORM` unset and `DISPLAY` pointing at SSH-forwarded X11, QApplication/XCB initialization blocks in libX11 C code; SIGALRM-based pytest-timeout cannot interrupt it. `test_ion_source_dropdown.py` and `test_custom_molecule_panel_34_6.py` create QApplication **without** setting offscreen — they are the likely members of the excluded 22.
**Workaround (verified):** always set `QT_QPA_PLATFORM=offscreen` (module-top `os.environ.setdefault` or fixture `monkeypatch.setenv`) before any Qt import/use. With offscreen set, QApplication + widget construction is fast and safe even with `DISPLAY` set (probe: MainWindow constructs in 0.4s under `DISPLAY=localhost:11.0 + offscreen`).

### Blocker 2: Modal dialogs — the complete catalog (probe-discovered; NONE of it documented anywhere today)
Driving real handlers surfaces modals from **multiple module namespaces**. Each hangs the test if unpatched. Verified catalog:

| Dialog | Namespace to patch | When it fires |
|---|---|---|
| `QMessageBox.information("Export Complete")` | `quickice.gui.main_window.QMessageBox` (`information` — **the one that hung my first probe**) | EVERY successful export via menu handler (`main_window.py` `_on_export_*_gromacs` success paths) |
| `QMessageBox.warning` (No Interface / No Hydrate / No Config / NaN-guard) | `quickice.gui.main_window.QMessageBox` | export/insert handlers on missing state or bad input |
| `QMessageBox.critical` (generation error) | `quickice.gui.main_window.QMessageBox` | worker error slots (`_on_interface_generation_error`, hydrate/ion error handlers) |
| `QMessageBox.question` (overwrite prompt) | `quickice.gui.export.QMessageBox` (whole class) | exporter when target file exists (export.py:761, 836) |
| `QFileDialog.getSaveFileName` | `quickice.gui.export.QFileDialog` | every export (once per call, for `.gro`) |
| `QMessageBox.question` (residue-name mismatch / generic name) | panel module's QMessageBox (`quickice.gui.custom_molecule_panel`) | `_validate_files()` → `_show_residue_mismatch_dialog()` when GRO resname ≠ ITP moleculetype (or generic "MOL") |
| `QMessageBox.warning` (missing `[atomtypes]`) | panel namespace | `_show_validation_warnings()` |
| `QMessageBox.question` ("Previous Custom Molecules Found") | `quickice.gui.main_window.QMessageBox` | `_on_insert_custom_molecule` re-insertion path (main_window.py:1253) |
| hydrate/ion/solute panel warnings | each panel module's QMessageBox (only 2 usages total, grep-verified) | rare paths |

**Workaround (verified):** patch each namespace's used methods (`patch.object(mwmod.QMessageBox, "warning", ...)` etc., or patch the whole class per namespace) **plus** the export module's QFileDialog. Return `QMessageBox.Yes` for question dialogs when the flow should proceed; `QMessageBox.Ok` otherwise. **A missed namespace = silent 120s+ hang, and pytest-timeout SIGALRM cannot break a modal `exec()`** (same C-level limitation as Blocker 1 — the probe hung until the external `timeout` killed it).

### Blocker 3: VTK rendering headless — crashes on real structures (TEST-06, now empirically characterized)
**Evidence (today's probes):** With `DISPLAY` **empty** + offscreen, `is_vtk_available()` returns **True** (empty DISPLAY bypasses the localhost heuristic) → MainWindow constructs VTK widgets fine (GL context creation logs shader errors but survives) — UNTIL a real structure is rendered: the interface render produced `vtkShaderProgram Could not create shader object` errors and, in one probe run, a hard `std::bad_array_new_length` C++ abort → core dump. This is ROADMAP TEST-06 ("VTK rendering may still crash in some headless environments"), now pinned to: **actor/widget construction is survivable; actual rendering of real structures is not reliable headless.**
**Workaround (verified):** set `DISPLAY=localhost:11.0` (with `QT_QPA_PLATFORM=offscreen`) so `is_vtk_available()` → False in every viewer; MainWindow then takes its documented no-VTK branches (`main_window.py:723-734` "3D viewer unavailable in remote environment" log path). Full chain ran with **zero VTK errors** and clean exit. This env combo is the recommended standard for MainWindow-level GUI e2e. (Alternative: `QUICKICE_FORCE_VTK=false` does NOT work — the heuristic only checks equality with `"true"` on localhost DISPLAYs, so any non-"true" value already yields False; setting DISPLAY is the simpler, already-tested lever.)

### Blocker 4: Thread teardown crash (SIGABRT/core dump) — poisons the pytest session
**Evidence (probe):** every probe that exited (normally OR via assertion failure) while a viewmodel/worker QThread was still alive died with `QThread: Destroyed while thread '' is still running` → `core dumped` (exit 134) — including the mid-test assertion failure case, because the cleanup code after the assert never ran. A pytest session where this happens reports a crash, not a clean failure, and can kill the run.
**Workaround (verified):** explicit teardown in the fixture (finalizer/`yield`-after): `thread.quit(); thread.wait(5000)` for every QThread the flow created (`_viewmodel._interface_thread`, `_viewmodel._thread`, `mw._custom_worker_thread`) and `.wait(5000)` for every worker (`_hydrate_worker`, `_ion_worker`, `_custom_worker`). Probe exited 0 with this cleanup, repeatedly.

### Blocker 5: Handler-created workers cannot be pre-connected
**Evidence (probe):** `mw._hydrate_worker` / `mw._ion_worker` are created **inside** the click handlers (`_on_hydrate_generate_clicked` at main_window.py:834, `_on_insert_ions`), so a test cannot connect to their signals before triggering. Naive connect-then-trigger races.
**Workaround (verified):** **state polling** — emit/call the trigger, then run a `QEventLoop` with a `QTimer.singleShot(80ms)` poll on `getattr(mw, "_current_hydrate_result")` (etc.) until non-None, with a hard `QTimer.singleShot(120000, loop.quit)` backstop, and patch `QMessageBox.critical` to capture error dialogs so failures are observable instead of hanging. (For viewmodel-owned signals like `interface_generation_complete`, pre-connect works fine since the viewmodel exists.)

### Blocker 6: GenIce2 runtime + gmx availability
Non-blockers, established: GenIce2 sI 1×1×1 generation via the real worker took **0.10–0.12s** in-probe (the "3–5s" figure in AGENTS.md is for heavier configs; module-scoping is still mandatory for multi-lattice matrices). `gmx` is on PATH in this environment (`/data/nglokwan/ompi_plumed-gmx/plumed-gromacs2023.5-gpu/bin/gmx`); `@gmx_skipif` (tests/conftest.py:24) keeps the suite green where it isn't. grompp on the probe's ~40k-atom system: ~1s.

### Blocker 7 (soft): first `import main_window` costs ~5.3s
VTK + PySide6 import chain. One-time per pytest process (module import), amortized across all tests in the file. Budget it; don't be alarmed by the first test's latency.

## 4. 45-Phase GUI e2e Assessment + UAT Bug Analysis (the phase's core evidence)

### 4.1 What Phase 45 built (14 plans, 52 tests, all passing)
Phase 45's GUI tests are **exporter-level** e2e: module-scoped GenIce2 fixtures → real structures → `*GROMACSExporter(parent_widget=None)` with QFileDialog/QMessageBox patched → `assert_itp_completeness` + `assert_gro_top_consistent` + `grompp rc=0`. Coverage is genuinely broad: 7 new lattices × interface export, 4 lattices × full 4-exporter cross-tab, sH full chain, water-only survival, triclinic blocking (CLI `_run_interface_step` + real `InterfaceGenerationWorker.run()`), triclinic 4×4×4 hydrate-only export, custom guest × 4 non-sI lattices, mixed built-in via GUI hydrate exporter. The **45-VERIFICATION.md** records 8/8 success criteria verified and explicitly lists the un-verified remainder as "human-only": (1) dialog visual appearance, (2) "Real-time GUI worker thread behavior — the async `QThread.start()`/`QEventLoop` path is not exercised".

### 4.2 Why UAT still found bugs afterward — the causal chain (verified in planning docs)

1. **45-UAT itself skipped all 3 GUI items**: tests 2, 5, 6 marked `skipped — "Requires GUI + human verification (headless environment)"`. The GUI tab chain was *never* programmatically UAT-verified; the e2e suite's exporter-level green was extrapolated to the GUI as a whole.
2. **44.1-UAT (Workflow F, manual, 2026-07-23) found the major bug**: Custom/Solute/Ion exports failed grompp with "moleculetype etoh is redefined" — duplicate `#include etoh.itp` because the cage-guest ITP (transformed to MOL_H) and the custom-molecule ITP (moleculetype etoh) share basename `etoh.itp`; both staged to the same output file, second overwrites first. **Why every e2e missed it:** 44.1-19's own fixture comment (test_e2e_custom_guest_cross_tab_gui.py:176-197) says it uses "a RENAMED COPY (cmet.gro/cmet.itp …) to avoid the etoh.itp filename collision" — the test fixture pre-solved the exact UX scenario that bites real users (uploading the same ethanol pair as both cage guest and custom molecule). The debug doc (`.planning/debug/resolved/uat-f-gui-custom-guest-issues.md`) states it plainly: "The CLI avoids the collision by pre-renaming, not by auto-rename in the exporter… The rename happens in the TEST FIXTURE, not the exporter."
3. **UAT Workflow F (2026-08-04) found 2 more**: Issue 1 — `validate_custom_guest_files` silently accepted an ITP whose `[atoms]` resname (ETHANOL) mismatched the GRO resname (MOL) → generation proceeded as if no custom guest existed (SILENT failure). Issue 2 — the collision above, root-caused to 3 writers + 3 exporter staging sites. Both were fixed (`atom_resname` validation; `_resolve_custom_molecule_itp_name` collision rename, verified in `tests/test_uat_f_custom_guest_fixes.py`).
4. **The structural lesson:** the e2e suite validates the *engine + exporters* on *curated fixtures*, while the bugs lived in (a) the **panel→handler→worker→exporter glue** (which only real MainWindow flow exercises) and (b) **realistic user input** (unrenamed files, mismatched resnames) which fixtures normalize away. 44.1-UAT's evidence and my probe's etoh finding are the same failure shape, 6 weeks apart.

### 4.3 Which 45-phase GUI tests still pass (verified today)
`test_e2e_custom_guest_cross_tab_gui.py` 4/4 (1.64s); `test_e2e_lattice_cross_tab_gui.py` + `test_e2e_builtin_cross_tab_regression.py` 8/8 (7.51s); triclinic blocking 4/4 (0.96s). The suite is healthy — the phase's job is not to repair it but to **add the missing execution-level layer** and re-anchor fixtures to realistic user inputs.

### 4.4 Live bug-class demonstration from this research (report to planner as a decision item, NOT auto-fix)
Driving the real panel flow with the *unrenamed* etoh pair (the normal user upload), answering the residue-mismatch dialog with **Yes** (the proceed path), yields: insertion OK (n=10), export writes `.top [molecules] … etoh 10` while `.gro` residues are `[CH4_H, MOL, SOL]`. `assert_gro_top_consistent` (the repo's own gate, stricter than GROMACS) calls this FATAL; **`gmx grompp` returns rc=0** (grompp matches by atom counts, not residue names). The dialog's "Yes" branch only updates labels (`residue_name_label`), not the structure's actual atom/residue names. Options for the planner: (a) treat as a real bug — make the "Yes" path actually rename residues (or make the custom writers emit the GRO residue name consistently), then assert strict consistency in the new e2e; or (b) keep grompp rc=0 as the authoritative gate for the custom path and document the name mismatch as cosmetic. **Either way, a true GUI e2e using realistic files surfaces this; the current suite cannot.**

## 5. Recommended GUI e2e Architecture + Runtime Budget

### 5.1 Architecture: one module-scoped "driven MainWindow" chain fixture + parametrized export/grompp cases

```
tests/e2e_gui/  (or tests/test_e2e_gui_fullchain.py at root, per 48.2 layout rules)
├── conftest or helpers: gui_e2e_helpers.py
│     - qapp_session fixture (session-scoped QApplication; offscreen forced)
│     - patch_gui_modals() context manager (complete §3-Blocker-2 catalog, parametrizable return values)
│     - wait_for_mainwindow_state(mw, attr, timeout_ms)  (Pattern-5c polling loop)
```

### 5.3 Hard rules for the planner (each backed by a probe failure or repo incident)

1. Every GUI test file sets `QT_QPA_PLATFORM=offscreen` at module top (or a session autouse fixture) **before** any Qt import. (Blocker 1 — the 22-test exclusion + 2-hour hang.)
2. MainWindow-level tests run under `DISPLAY=localhost:11.0` (or any non-empty localhost DISPLAY) so `is_vtk_available()`→False; never render real structures headless. (Blocker 3 — TEST-06.)
3. Patch the **complete** modal catalog per §3-Blocker-2 — one missed `QMessageBox.information` = a hung test that pytest-timeout cannot kill. (Probe-verified twice.)
4. Fixture teardown MUST `quit()+wait()` all threads; also guard against assertion-failure paths skipping cleanup (use `try/finally` or pytest finalizers). (Blocker 4 — SIGABRT.)
5. Wait on state attributes with a polling event loop for handler-created workers; connect directly only to viewmodel signals. (Blocker 5.)
6. Module-scope the MainWindow + chain fixture; one `MainWindow` per module max (multiple constructions work but waste ~0.4s each and multiply thread-teardown surface).
7. Keep exporter-level e2e files as-is (48.2 explicitly preserved CLI/GUI e2e sibling pairs); the new layer complements, not replaces.
8. New e2e must use **realistic (unrenamed) user files** for at least one custom-molecule case — that is the single highest-value change, per §4. (Coordinate with the CLI AREA on the mirror decision.)
